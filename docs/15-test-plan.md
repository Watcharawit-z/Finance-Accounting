# 15 — แผนการทดสอบและเกณฑ์การยอมรับ

## 1. หลักการ

ระบบบัญชีต่างจากซอฟต์แวร์ทั่วไปตรงที่ **บั๊กเรื่องตัวเลขคือความเสียหายทางกฎหมาย**
ไม่ใช่แค่ประสบการณ์ใช้งานที่ไม่ดี แผนทดสอบจึงถ่วงน้ำหนักไปที่ความถูกต้องของตัวเลขและ
การบังคับกฎ มากกว่าการทดสอบ UI

| ระดับ | สัดส่วน | ครอบคลุมอะไร |
|-------|---------|--------------|
| Database rules | — | กฎที่บังคับด้วย constraint/trigger (`db/tests/`) |
| Unit | ~60% | การคำนวณภาษี ต้นทุน ค่าเสื่อม การปัดเศษ |
| Integration | ~30% | flow ข้ามโมดูล (ออกใบกำกับ → ลงบัญชี → เข้ารายงานภาษี) |
| End-to-end | ~10% | เส้นทางที่ผู้ใช้ทำจริง ผ่านเบราว์เซอร์ |

**เกณฑ์บังคับ:** โมดูล `core-ledger` และ `core-tax` ต้องมี coverage ≥ 95%
โมดูลอื่น ≥ 80% — และ coverage ไม่ใช่เป้าหมาย แต่เป็นพื้นขั้นต่ำ

## 5. Integration test — เส้นทางข้ามโมดูล

แต่ละเส้นทางต้องตรวจ **ทุกผลลัพธ์ที่เกิดขึ้น** ไม่ใช่แค่ HTTP 200

```
เส้นทาง A: ขายเชื่อ → รับชำระ
  1. สร้างใบกำกับภาษี 107,000 (สินค้า 100,000 + VAT 7,000)
  → ตรวจ: JE เดบิตลูกหนี้ 107,000 / เครดิตรายได้ 100,000 + ภาษีขาย 7,000
  → ตรวจ: tax_transaction 1 แถว kind=vat_output
  → ตรวจ: stock_move ตัดสต๊อกและสร้าง JE ต้นทุนขาย
  → ตรวจ: เลขที่เอกสารเรียงต่อจากใบก่อนหน้า
  → ตรวจ: partner_snapshot มีข้อมูลคู่ค้าครบ
  2. รับชำระ 104,000 (ลูกค้าหัก WHT 3,000)
  → ตรวจ: JE เดบิตธนาคาร 104,000 + ภาษีถูกหัก 3,000 / เครดิตลูกหนี้ 107,000
  → ตรวจ: สถานะใบกำกับเป็น paid
  → ตรวจ: ยอดลูกหนี้คงเหลือ = 0
  3. ปิดงวดและยื่น ภ.พ.30
  → ตรวจ: ภาษีขายในรายงาน = 7,000 = ยอดบัญชี 2141
  → ตรวจ: หลังยื่นแล้ว แก้ใบกำกับไม่ได้

เส้นทาง B: ซื้อเชื่อ → จ่ายชำระพร้อมหัก ณ ที่จ่าย
  → ตรวจ: 50 ทวิ ออกอัตโนมัติพร้อมเลขที่เล่ม/เลขที่
  → ตรวจ: รายการเข้า ภ.ง.ด.53 ถูกต้อง
  → ตรวจ: ถ้าตั้ง remittance_channel = e_wht แล้ว ต้องไม่เข้า ภ.ง.ด.53

เส้นทาง C: ปิดงวดเดือน
  → ตรวจ: บล็อกเมื่อยังมี draft ค้าง
  → ตรวจ: บล็อกเมื่อบัญชีพักไม่เป็นศูนย์
  → ตรวจ: หลังปิดแล้ว ลงรายการย้อนหลังไม่ได้

เส้นทาง D: ปิดปีบัญชี
  → ตรวจ: ปิดบัญชีรายได้-ค่าใช้จ่ายเข้ากำไรสะสมครบ
  → ตรวจ: จัดสรรสำรองตามกฎหมาย 5% ถูกต้อง และหยุดที่ 10% ของทุน
  → ตรวจ: ยอดยกไปปีถัดไปตรงกับงบแสดงฐานะการเงิน

เส้นทาง E: กลับรายการ
  → ตรวจ: ยอดสุทธิเป็น 0 ทุกบัญชี
  → ตรวจ: รายการเดิมยังปรากฏในบัญชีแยกประเภท (ไม่หายไป)
  → ตรวจ: audit trail แสดงทั้งสองรายการพร้อมความเชื่อมโยง
```

## 7. Reconciliation test (รันทุกคืนบน production)

Job ที่ต้องรันอัตโนมัติและแจ้งเตือนทันทีเมื่อไม่ตรง:

```
[ ] Σ ลูกหนี้รายราย        = ยอดบัญชีคุมลูกหนี้ (1131–1134)
[ ] Σ เจ้าหนี้รายราย        = ยอดบัญชีคุมเจ้าหนี้ (2121–2124)
[ ] Σ มูลค่าสินค้าคงเหลือ    = ยอดบัญชีสินค้าคงเหลือ (1151–1156)
[ ] Σ ภาษีขายในทะเบียน      = ยอดบัญชีภาษีขาย (2141)
[ ] Σ ภาษีซื้อในทะเบียน      = ยอดบัญชีภาษีซื้อ (1161)
[ ] Σ ภาษีหัก ณ ที่จ่ายค้าง  = ยอดบัญชี 2144–2147
[ ] Σ มูลค่าทรัพย์สินสุทธิ   = ยอดบัญชีทรัพย์สิน − ค่าเสื่อมสะสม
[ ] Σ เดบิต − Σ เครดิต ทั้งฐานข้อมูล = 0
[ ] ยอดบัญชีพัก (9910) = 0
```
ผลบันทึกลงตาราง `reconciliation_check` — ผู้สอบบัญชีเรียกดูได้

## 10. การยอมรับโดยผู้ใช้ (UAT)

**ต้องทำโดยนักบัญชีจริง ไม่ใช่นักพัฒนา**

| รอบ | ขอบเขต | เกณฑ์ผ่าน |
|-----|--------|-----------|
| UAT 1 | คีย์เอกสาร 1 เดือนคู่ขนานกับระบบเดิม | ตัวเลขตรงกัน 100% |
| UAT 2 | ปิดงบเดือนเต็มรูปแบบ | ปิดได้ภายใน 5 วันทำการ |
| UAT 3 | ยื่นภาษีจริงจากระบบ | ยื่นผ่านทุกแบบ ไม่มีการแก้ไขเพิ่มเติม |
| UAT 4 | ปิดงบปีและให้ผู้สอบบัญชีตรวจ | ผู้สอบบัญชียอมรับเอกสารที่ส่งออกจากระบบ |

**เกณฑ์บล็อกการ go-live**
```
✗ มีบั๊กระดับ critical ที่ทำให้ตัวเลขผิด — ห้ามขึ้นระบบเด็ดขาด
✗ ยอดยกมาไม่ตรงกับระบบเดิม
✗ reconciliation job ยังไม่ผ่านครบทุกข้อ
✗ ยังไม่ทดสอบกู้คืนข้อมูลจริง
✗ ผู้สอบบัญชียังไม่รีวิวเอกสารที่ระบบออก
```

## 11. CI Pipeline

```
ทุก push:
  1. lint + typecheck
  2. unit test + coverage gate
  3. db/tests/run.sh บน PostgreSQL ที่สร้างใหม่
  4. integration test บน docker-compose
  5. ตรวจว่า migration ใหม่รันบนฐานข้อมูลที่มีข้อมูลเดิมได้ (ไม่ใช่แค่ฐานว่าง)

ทุกคืน:
  6. property-based test แบบเต็มจำนวน
  7. performance test
  8. dependency scan + SBOM

ก่อน release:
  9. E2E บนเบราว์เซอร์จริง
 10. ทดสอบพิมพ์เอกสารทุกแบบฟอร์ม (เทียบภาพกับไฟล์อ้างอิง)
 11. ทดสอบ restore จาก backup
```
