# 07 — ความปลอดภัย การควบคุมภายใน และ PDPA

## 1. บทบาทและสิทธิ์ (RBAC)

### 1.1 บทบาทมาตรฐาน

| บทบาท | ทำได้ | ทำไม่ได้ |
|-------|-------|----------|
| **เจ้าของ / กรรมการ** | ดูทุกอย่าง, อนุมัติวงเงินสูงสุด, จัดการผู้ใช้ | — |
| **ผู้บริหาร (CFO)** | ดูทุกรายงาน, อนุมัติ, ปลดล็อกงวด | แก้ผังบัญชีโดยตรง |
| **สมุห์บัญชี** | ลงบัญชี, ปิดงวด, ยื่นภาษี, จัดการผังบัญชี | อนุมัติจ่ายเงินของตัวเอง, จัดการผู้ใช้ |
| **พนักงานบัญชี** | คีย์เอกสาร, สร้าง JE ฉบับร่าง | ลงบัญชีขั้นสุดท้าย, ปิดงวด, ดูเงินเดือน |
| **การเงิน (Treasury)** | สร้างรายการจ่าย, กระทบยอดธนาคาร | สร้างผู้ขายใหม่ (แยกหน้าที่) |
| **จัดซื้อ** | PR/PO/รับของ | ตั้งหนี้, จ่ายเงิน |
| **ขาย** | ใบเสนอราคา, ใบสั่งขาย, ดูวงเงินลูกค้า | ดูต้นทุน, ดูกำไร, เข้าถึง GL |
| **คลังสินค้า** | รับ/จ่าย/โอน/นับสต๊อก | เห็นราคาทุนต่อหน่วย (ตัวเลือก) |
| **HR/เงินเดือน** | ข้อมูลพนักงาน, ทำเงินเดือน | โมดูลอื่นทั้งหมด |
| **ผู้สอบบัญชี** | **อ่านอย่างเดียว** ทุกรายการ + audit log + ดาวน์โหลดหลักฐาน | แก้ไขใด ๆ |
| **ผู้ดูแลระบบ** | ผู้ใช้, การตั้งค่า, การเชื่อมต่อ | **ดูหรือแก้ตัวเลขทางบัญชี** (สำคัญ) |

### 1.2 การแยกหน้าที่ (Segregation of Duties) ที่ระบบต้องบังคับ
- คนสร้างผู้ขาย ≠ คนสร้างรายการจ่ายให้ผู้ขายนั้น
- คนคีย์เอกสาร ≠ คนอนุมัติ ≠ คนลงบัญชีขั้นสุดท้าย (อย่างน้อย 2 คน)
- คนกระทบยอดธนาคาร ≠ คนมีสิทธิ์สั่งโอน
- ระบบต้อง **เตือนเมื่อการตั้งค่าสิทธิ์ละเมิดหลักนี้** และให้ log ไว้ว่าใครยอมรับความเสี่ยง

### 1.3 สิทธิ์ระดับข้อมูล
```
user_company_role: user_id, company_id, role_id,
                   scope_json { branch_ids:[], department_ids:[], project_ids:[] }
```
บังคับผ่าน PostgreSQL RLS + ตรวจซ้ำที่ชั้น service (defense in depth)

## 2. การควบคุมภายใน (Internal Control) ที่ฝังในระบบ

| การควบคุม | วิธีทำ |
|-----------|--------|
| ห้ามแก้เอกสารที่ลงบัญชีแล้ว | Trigger ระดับ DB block UPDATE/DELETE |
| ห้ามลงรายการในงวดที่ปิดแล้ว | ตรวจที่ `LedgerService.post()` + constraint |
| วงเงินอนุมัติ | ตาราง `approval_flow` ตามประเภท×จำนวนเงิน×แผนก |
| การตรวจสอบยอดคุม | Job รายวันเทียบ ลูกหนี้ย่อย=บัญชีคุม, สินค้าคงเหลือ=บัญชีคุม, ภาษี=บัญชีภาษี → แจ้งเตือนถ้าต่าง |
| การตรวจจับรายการผิดปกติ | JE ที่ลงนอกเวลาทำการ, JE ยอดกลม ๆ ผิดปกติ, JE ที่คนคนเดียวสร้างและ post เอง |
| เลขที่เอกสารขาดช่วง | รายงาน "เลขที่หายไป" ให้ผู้สอบบัญชีตรวจ |
| การเปลี่ยนแปลงข้อมูลหลัก | ผู้ขาย/เลขบัญชีธนาคาร เปลี่ยนแล้วต้องอนุมัติซ้ำ + แจ้งเตือน (กันฉ้อโกงเปลี่ยนเลขบัญชี) |

## 3. ความปลอดภัยทางเทคนิค

| ชั้น | มาตรการ |
|-----|---------|
| การยืนยันตัวตน | รหัสผ่าน (Argon2id) + **MFA บังคับ** สำหรับ role ที่แตะเงิน, SSO/OIDC สำหรับองค์กร |
| Session | JWT อายุสั้น 15 นาที + refresh token หมุนเวียน, จำกัดจำนวน session, บังคับออกจากระบบทุกเครื่องได้ |
| การเข้ารหัส | TLS 1.3 ระหว่างทาง, AES-256 ที่เก็บ, เข้ารหัสระดับคอลัมน์สำหรับเลขบัตร ปชช./เลขบัญชี/เงินเดือน |
| กุญแจ | AWS KMS / HSM, private key ของ e-Tax อยู่ใน service แยกที่ไม่มี inbound จากอินเทอร์เน็ต |
| ไฟล์แนบ | สแกนไวรัส, ตรวจ MIME จริง (ไม่เชื่อนามสกุล), ให้ลิงก์แบบ signed URL หมดอายุ 5 นาที |
| แอปพลิเคชัน | ป้องกัน OWASP Top 10, prepared statement เท่านั้น, CSP เข้ม, ไม่มี `eval` |
| โครงสร้างพื้นฐาน | VPC แยก subnet, security group ขั้นต่ำ, ไม่มี public IP บน DB, bastion + audit |
| การตรวจสอบ | SIEM, แจ้งเตือน login ผิดปกติ, geo-anomaly, การดาวน์โหลดข้อมูลจำนวนมาก |
| ทดสอบเจาะระบบ | Pentest ก่อน go-live และทุกปี, bug bounty เมื่อเปิดขาย |
| ห่วงโซ่อุปทาน | SBOM, สแกน dependency ทุก build, pin เวอร์ชัน |

## 4. PDPA — พ.ร.บ.คุ้มครองข้อมูลส่วนบุคคล พ.ศ. 2562

### 4.1 บทบาทของเรา
- **ใช้ภายในบริษัท:** บริษัทเป็น *ผู้ควบคุมข้อมูล* (Data Controller)
- **เปิดขายเป็น SaaS:** เราเป็น *ผู้ประมวลผลข้อมูล* (Data Processor) → ต้องมี **DPA** แนบสัญญาทุกราย

### 4.2 ข้อมูลส่วนบุคคลที่ระบบถือครอง

| ข้อมูล | ที่ไหน | ฐานทางกฎหมาย | ความอ่อนไหว |
|--------|--------|----------------|--------------|
| ชื่อ-ที่อยู่-เลขผู้เสียภาษีลูกค้าบุคคลธรรมดา | partner, tax_transaction | หน้าที่ตามกฎหมาย (ออกใบกำกับภาษี) | ปานกลาง |
| เลขบัตรประชาชนพนักงาน | employee | หน้าที่ตามกฎหมาย (ภ.ง.ด.1, ประกันสังคม) | **สูง** |
| เงินเดือน/รายได้ | pay_slip | สัญญาจ้าง | **สูง** |
| เลขบัญชีธนาคาร | partner, employee | สัญญา | **สูง** |
| ข้อมูลสุขภาพ (ถ้ามีสวัสดิการ) | — | ความยินยอมชัดแจ้ง | **อ่อนไหวพิเศษ ม.26** — หลีกเลี่ยงการเก็บ |

### 4.3 สิทธิเจ้าของข้อมูล vs หน้าที่เก็บเอกสาร 5 ปี
**จุดที่ขัดกันและวิธีจัดการ:**
```
ลูกค้าขอลบข้อมูล → ระบบตรวจว่าข้อมูลนั้นผูกกับเอกสารทางภาษีหรือไม่
   ถ้าใช่  → ปฏิเสธคำขอโดยอ้าง ม.33(3) "ปฏิบัติตามกฎหมาย"
             บันทึกคำขอ + เหตุผลปฏิเสธ + แจ้งกลับเป็นลายลักษณ์อักษร
             ตั้ง flag ให้ลบอัตโนมัติเมื่อพ้น retention
   ถ้าไม่  → ลบจริง (hard delete) + บันทึกใน audit log
```
ระบบต้องมีหน้า **"คำขอใช้สิทธิ"** ที่จัดการครบ: เข้าถึง, สำเนา, แก้ไข, ลบ, คัดค้าน, ระงับใช้, โอนย้าย
พร้อม SLA 30 วันตามกฎหมาย

### 4.4 สิ่งที่ต้องมีเป็นเอกสาร
- บันทึกรายการประมวลผล (RoPA)
- นโยบายความเป็นส่วนตัว (ไทย/อังกฤษ)
- ข้อตกลงประมวลผลข้อมูล (DPA) สำหรับลูกค้า SaaS
- รายชื่อผู้ประมวลผลช่วง (Sub-processor list) — AWS, ผู้ให้บริการอีเมล, e-Tax provider
- แผนรับมือเหตุละเมิดข้อมูล — **แจ้ง สคส. ภายใน 72 ชั่วโมง**
- แต่งตั้ง DPO ถ้าเข้าเงื่อนไข (ประมวลผลข้อมูลจำนวนมากเป็นกิจกรรมหลัก)

### 4.5 การเก็บและทำลายข้อมูล

| ประเภท | เก็บ | หลังจากนั้น |
|--------|------|-------------|
| เอกสารบัญชี/ภาษี + ไฟล์แนบ | 5 ปี (ตั้งได้ถึง 10) นับจากสิ้นรอบบัญชี | ทำลายอัตโนมัติ + บันทึกหลักฐานการทำลาย |
| Audit log | 7 ปี | archive แล้วทำลาย |
| ข้อมูลพนักงานที่ลาออก | 10 ปี (อายุความคดีแรงงาน/ภาษี) | ทำลาย |
| Log ระบบ (access log) | 90 วันออนไลน์ + 1 ปีใน cold storage | ทำลาย |
| ข้อมูลลูกค้าที่ยกเลิกบริการ (SaaS) | 90 วันให้ export ได้ | ลบทั้ง tenant + แจ้งยืนยัน |

## 5. ความต่อเนื่องทางธุรกิจ

- **สิทธิ์ในข้อมูลของลูกค้า:** ลูกค้า export ข้อมูลทั้งหมดของตัวเองได้ตลอดเวลา (SQL dump + CSV + ไฟล์แนบ)
  — เขียนในสัญญาให้ชัด ไม่ล็อกลูกค้าไว้กับระบบ
- **Escrow ซอร์สโค้ด** สำหรับลูกค้า Enterprise (ถ้าบริษัทเราปิดตัว ลูกค้ายังใช้ระบบต่อได้)
- ซ้อมกู้คืนระบบทุกไตรมาส บันทึกผลเป็นหลักฐาน
