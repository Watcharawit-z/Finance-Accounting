# 14 — วงจรสถานะเอกสาร และรหัสข้อผิดพลาด

## 1. หลักการ

1. สถานะทุกเอกสารใช้ enum เดียวกันทั้งระบบ (`doc_status`) — UI และรายงานเขียนครั้งเดียว
2. **การเปลี่ยนสถานะที่ไม่อยู่ในแผนภาพ = ต้องถูกปฏิเสธ** ไม่ใช่แค่ไม่มีปุ่มบน UI
3. เอกสารที่ลงบัญชีแล้ว ไม่มีทางกลับไปเป็นฉบับร่างได้ ทำได้แค่ยกเลิก (void) พร้อมกลับรายการ
4. ทุกการเปลี่ยนสถานะบันทึกลง `audit_event` พร้อมผู้กระทำและเหตุผล

## 2. ใบเสนอราคา (Quotation)

```
  draft ──approve──► pending_approval ──approve──► issued
    │                      │                        │
    │                   reject                   ┌──┴──┬────────┐
    ▼                      ▼                     │     │        │
 cancelled              rejected            expired  cancelled  closed
                                                            (แปลงเป็นใบสั่งขาย)
```
- `expired` ตั้งอัตโนมัติเมื่อพ้น `valid_until` (job รายวัน)
- ไม่มีผลทางบัญชี ไม่สร้าง JE

## 3. ใบสั่งขาย (Sales Order)

```
  draft ──confirm──► approved ──deliver──► partially_received ──►  closed
    │                   │                          │                  ▲
    │                   │                          └──────deliver─────┘
    ▼                   ▼
 cancelled          cancelled  (ยกเลิกได้ตราบใดที่ยังไม่ส่งของ)
```
- จองสต๊อก (`stock_balance.reserved_qty`) เมื่อเข้าสู่ `approved`
- คืนการจองเมื่อ `cancelled`

## 4. ใบกำกับภาษี (Sales Invoice) — สำคัญที่สุด

```
                          ┌──── void ◄──── (กลับรายการ + ลายน้ำ "ยกเลิก")
                          │                  ต้องยังไม่ถูกรับชำระ และงวดยังเปิด
  draft ──issue──► issued ┼──receive──► partially_paid ──receive──► paid
    │                │    │                    │                      │
    │                │    └─── credit_note ────┴──────────────────────┘
    ▼                │           (ลดหนี้บางส่วน/ทั้งจำนวน)
 cancelled           │
 (ยังไม่ออกเลข)      └─► e-Tax: pending → signed → submitted → accepted
                                                          └──► rejected → แก้แล้วส่งใหม่
```

**สิ่งที่เกิดขึ้นตอน `issue` (ต้องอยู่ใน transaction เดียวกันทั้งหมด)**
```
1. ตรวจ validator ทั้งหมด (ดูรายการใน docs/11 ข้อ 1.3)
2. จองเลขที่เอกสารและเลขที่ใบกำกับภาษีจาก document_sequence
3. บันทึก partner_snapshot จากข้อมูลคู่ค้า ณ ขณะนั้น
4. สร้าง journal_entry + journal_line ผ่าน LedgerService
5. สร้าง tax_transaction (kind = vat_output)
6. ตัดสต๊อกและสร้าง stock_move (ถ้าเป็นสินค้า)
7. เข้าคิว e-Tax ถ้าบริษัทเปิดใช้
8. บันทึก audit_event
```
ถ้าข้อใดล้มเหลว → rollback ทั้งหมด รวมถึงเลขที่เอกสาร (ไม่ commit sequence)

**กฎการ void**
```
void ได้เมื่อ:  ยังไม่มีการรับชำระ  AND  ยังไม่มีใบลดหนี้อ้างอิง
                AND งวดบัญชียังเปิดอยู่  AND ยังไม่ยื่น ภ.พ.30 ของงวดนั้น
void ไม่ได้เมื่อ: งวดปิดแล้ว → ต้องออก "ใบลดหนี้" แทน
ผลลัพธ์:        เลขที่เอกสารยังคงอยู่ (ห้ามนำกลับมาใช้)
                สร้าง journal_entry กลับรายการ
                สร้าง tax_transaction กลับรายการ
                บันทึกลง voided_document_no พร้อมเหตุผล
```

## 5. ใบเสร็จรับเงิน (Receipt)

```
  draft ──post──► issued ──►(ตัดใบแจ้งหนี้ตาม receipt_allocation)
    │               │
    ▼               └── void ── (เฉพาะกรณีเช็คคืน หรือคีย์ผิดในงวดเดียวกัน)
 cancelled
```
- เมื่อรับเป็นเช็ค: สร้าง `cheque` สถานะ `on_hand` → ยังไม่ตัดลูกหนี้จนกว่าเช็คจะ `cleared`
  (หรือตัดทันทีเข้าบัญชี "เช็ครับลงวันที่ล่วงหน้า" 1134 แล้วแต่นโยบายบริษัท)
- เช็คคืน (`bounced`) → กลับรายการอัตโนมัติ + ตั้งลูกหนี้กลับ + คิดค่าธรรมเนียม

## 6. ใบสั่งซื้อ (Purchase Order)

```
  draft ──submit──► pending_approval ──approve──► approved ──send──► issued
    │                      │                                          │
    │                    reject                              ┌────────┼────────┐
    ▼                      ▼                                 ▼        ▼        ▼
 cancelled              rejected                    partially_received  received  closed
```
- ระบบตรวจงบประมาณตอน `submit` → ผลลัพธ์ `ok` / `warning` / `over_budget`
  (บล็อกหรือแค่เตือน ขึ้นกับ `budget.control_mode`)

## 7. ตั้งหนี้ผู้ขาย (Vendor Bill)

```
  draft ──match──► pending_approval ──approve──► issued ──pay──► partially_paid ──► paid
    │                    │                         │
    ▼                  reject                      └── void (งวดยังเปิด และยังไม่จ่าย)
 cancelled
```
**การจับคู่ 3 ทาง (3-way match) ตอน `match`**
```
matched          : PO = GR = Bill  ทั้งปริมาณและราคา
qty_variance     : ปริมาณต่างกัน   → ต้องอนุมัติเพิ่ม
price_variance   : ราคาต่างกัน     → ต้องอนุมัติเพิ่ม
no_po            : ไม่มี PO อ้างอิง → ต้องอนุมัติจากผู้มีอำนาจสูงขึ้น
```

## 8. ใบสำคัญจ่าย (Payment Voucher)

```
  draft ──submit──► pending_approval ──approve──► approved ──pay──► issued
    │                     │                                          │
    ▼                   reject                                       └── void
 cancelled                                              (เฉพาะกรณีเช็คยังไม่ส่ง/ยกเลิกเช็ค)
```
**สิ่งที่เกิดขึ้นตอน `pay`**
```
1. คำนวณและหักภาษี ณ ที่จ่ายตามอัตรา ณ วันจ่าย
2. ถ้า remittance_channel = 'manual' → สร้าง wht_certificate (50 ทวิ) + tax_transaction
   ถ้า = 'e_wht' → สร้าง tax_transaction แต่ไม่ออก 50 ทวิ (ธนาคารออกให้)
3. ตัดยอดเจ้าหนี้ตาม payment_allocation
4. สร้าง journal_entry
5. ถ้าจ่ายเป็นเช็ค → สร้าง cheque สถานะ prepared
```

## 9. งวดบัญชี (Accounting Period)

```
  open ──soft_close──► soft_closed ──close──► closed ──file_tax──► tax_filed
   ▲                        │                    │
   └────── reopen ──────────┘                    │  (ปลดล็อกได้ แต่ต้องบันทึกเหตุผล
   └───────────── reopen (เฉพาะ role สูง) ───────┘   และแจ้งเตือนผู้บริหาร)

  tax_filed = ล็อกถาวร ปลดไม่ได้
```
เงื่อนไขก่อนปิดงวด — ระบบต้องบล็อกถ้ายังไม่ครบ:
```
[ ] ไม่มีเอกสารสถานะ draft ค้างในงวด
[ ] ไม่มีคำขออนุมัติค้าง
[ ] บัญชีพัก (suspense) ยอดเป็นศูนย์
[ ] รายการธนาคารกระทบยอดครบ หรือมีรายการค้างที่อธิบายได้
[ ] ยอดลูกหนี้ย่อยรวม = บัญชีคุมลูกหนี้
[ ] ยอดเจ้าหนี้ย่อยรวม = บัญชีคุมเจ้าหนี้
[ ] ยอดสินค้าคงเหลือ = บัญชีคุมสินค้า
[ ] ยอดภาษีขายในรายงาน = บัญชีภาษีขาย
[ ] ยอดภาษีซื้อในรายงาน = บัญชีภาษีซื้อ
[ ] ค่าเสื่อมราคาประจำงวดลงบัญชีแล้ว
[ ] รายการปรับปรุงประจำงวดครบ (ค่าใช้จ่ายค้างจ่าย รายได้ค้างรับ)
[ ] งาน work_task ที่ blocking_close = true เสร็จหมดแล้ว
```

## 10. คำขออนุมัติ (Approval Request)

```
  pending ──approve(ทุกขั้น)──► approved ──► (ดำเนินการต่อกับเอกสารต้นทาง)
     │
     ├── reject ──► rejected ──► (เอกสารต้นทางกลับเป็น draft พร้อมความเห็น)
     └── cancel ──► cancelled  (ผู้ขอยกเลิกเอง)
```
- ผู้อนุมัติเป็นคนเดียวกับผู้ขอ → ข้ามขั้นนั้นถ้า `can_skip_if_same_user`
  แต่ต้องบันทึกว่า "ข้ามเพราะเป็นบุคคลเดียวกัน" ใน audit log

## 11. รหัสข้อผิดพลาด (Error Catalog)

รูปแบบ response มาตรฐาน:
```json
{ "error": { "code": "PERIOD_CLOSED",
             "message": "งวดบัญชี 2569-01 ปิดแล้ว ลงรายการไม่ได้",
             "message_en": "Accounting period 2026-01 is closed",
             "hint": "ขอปลดล็อกงวด หรือเปลี่ยนวันที่เป็นงวดถัดไป",
             "field": "posting_date",

             "request_id": "req_01HXYZ..." } }
```

## 12. หลักการเขียนข้อความผิดพลาด

```
✗ "เกิดข้อผิดพลาด กรุณาลองใหม่"
✗ "Error: null value in column original_invoice_id violates not-null constraint"
✓ "ออกใบลดหนี้ไม่ได้เพราะยังไม่ได้เลือกใบกำกับภาษีเดิม
   กฎหมายกำหนดให้ใบลดหนี้ต้องอ้างอิงใบกำกับภาษีที่ออกไปแล้วเสมอ
   [เลือกใบกำกับภาษี]"
```
ทุกข้อความต้องตอบ 3 คำถาม: **เกิดอะไรขึ้น · ทำไม · จะแก้ยังไง**
และมีปุ่มพาไปแก้ตรงจุดเมื่อทำได้
